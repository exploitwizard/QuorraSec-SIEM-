QUESTION 3: Does evaluate_custom_rules() actually run rule logic or just return?
─────────────────────────────────────────────────────────────────────────────
ANSWER: YES, it does run rule logic — but only for the FIRST matching rule

QUESTION 4: Does the Python DSL level actually exec() the rule code?
─────────────────────────────────────────────────────────────────────────────
ANSWER: YES.
rule_builder.py PythonDSLRunner.execute() → _exec_restricted() or _exec_basic()
Both use exec(compiled_code, globals, locals) and call the rule() function.
RestrictedPython sandbox is used when installed. The sandbox blocks bare
"import re" statements inside rule code — resolved by the sandbox toggle.

QUESTION 5: Does the YAML/JSON DSL actually evaluate conditions?
─────────────────────────────────────────────────────────────────────────────
ANSWER: YES.
rule_builder.py RuleEvaluator.evaluate() correctly parses conditions[] and
logic (AND/OR), applies _apply_operator() for all 12 simple operators,

QUESTION 6: Does the visual builder actually check conditions against log fields?
─────────────────────────────────────────────────────────────────────────────
ANSWER: YES.
Level 1 (visual) rules store their conditions as JSON in rule_definition
(same format as Level 2). evaluate_custom_rules handles both with:

The same RuleEvaluator processes both levels.

BUG 1 — CRITICAL: Custom rules silently skipped when any built-in rule fires
─────────────────────────────────────────────────────────────────────────────
File: app/rules_engine.py, lines 88–93
Code:
    # Custom rules (Levels 1, 2, 3)
    if not results["triggered"]:          ← BUG: this guard
        r = self.evaluate_custom_rules(log_entry)
        if r["triggered"]:
            results.update(r)

If ANY of the five built-in rules fires (brute_force, geo_velocity,
admin_privilege, os_command_injection, multiple_attack_types), the entire
custom rules evaluation is skipped. Custom rules are never evaluated for
real-world logs that trigger even one built-in rule.

Fix: Remove custom rules from check_rules entirely. Add a standalone
evaluate_all_custom_rules() called unconditionally from _process_ingest
after check_rules completes.

BUG 2 — HIGH: Only the first matching custom rule fires per log
─────────────────────────────────────────────────────────────────────────────
File: app/rules_engine.py, lines 354–375
Code:
    if triggered:
        ...
        return {      ← returns immediately on first match
            "triggered": True,
            ...
        }

After one custom rule triggers, the for-loop is exited. Any remaining
custom rules are never evaluated for that log event. If an org has 10
custom rules and events 2, 5, 8 all match, only the first is reported.

Fix: Iterate ALL rules without early return. Create an Alert + Attack
record for each matched rule.

BUG 3 — HIGH: No sandbox toggle — Python DSL always sandboxed
─────────────────────────────────────────────────────────────────────────────
The RestrictedPython sandbox blocks bare "import re" inside rule functions,
making regex-based detection rules impossible without workarounds. There is
no per-organisation setting to allow trusted admins to use full Python.

No OrganisationSettings model exists.
No /api/settings/sandbox endpoint exists.
No sandbox toggle in the UI exists.

Fix: Add OrganisationSettings model with python_dsl_sandbox column (default
True). Add API endpoints. Add unsandboxed execution path. Add UI toggle.

OBSERVATION: evaluate_custom_rules misses YAML fallback in L2
─────────────────────────────────────────────────────────────────────────────
File: app/rules_engine.py, line 343
Code:
    rule_def = json.loads(rule.rule_definition)

If rule_definition was saved as YAML text (not JSON), this raises
JSONDecodeError and the rule silently errors out. RuleEvaluator.parse_yaml()
handles YAML correctly but is never called from evaluate_custom_rules.

Fix: Try JSON first, then fall back to YAML in the new evaluation path.
